---
title: Webhook でワークフローを開始する
---

ほかのサービスからリクエストが届いたときに、ワークフローを開始できます。Issue が作られたときの GitHub、支払いが完了したときの Stripe、送信されたときのフォーム、Zapier や Make がつなぐアプリなどです。お使いのコンピューターには公開アドレスがないため、リクエストは Kitewell のリレーに届き、リレーがコンピューターの Kitewell に渡します。ポートを開ける必要も、トンネルを用意する必要もありません。

Webhook は Kitewell Pro の機能で、Kitewell が Dagu Cloud に[サインイン](/ja/docs/cloud-sync/#サインイン)している必要があります。

## Webhook をオンにする

1. 保存済みのワークフローを開き、**スケジュール**を選びます。**実行タイミング**のカードからも開けます。
2. **Webhook** の **オンにする** を選びます。少しすると URL が表示されます：`https://hooks.kitewell.app/…`
3. **コピー** を選び、リクエストを送るサービスに URL を貼り付けます。
4. **テストリクエストを送信** を選ぶと、経路全体を試せます。Kitewell が自分の URL にリクエストを送り、ほかのリクエストと同じくリレーを通って戻ってきます。実際のリクエストと同じく実行が 1 回始まり、**最近のリクエスト**でそのリクエストが開いて、届いた内容を確認できます。

オンにすると、**実行タイミング**のカードに **Webhook オン** と表示されます。URL を見られるのは、ワークフローを編集できる人だけです。API キーや接続済みのアプリからは読み取れません。

## アシスタントにリクエストを使わせる

リクエストの中身の形を知らなくても使えます。

1. 実際のサービスからリクエストを 1 件送らせます。たとえば GitHub でテスト用の Issue を作ります。
2. **最近のリクエスト**で、そのリクエストの **詳細** を選び、届いた内容を確認します。
3. **このリクエストからステップを作る** を選びます。アシスタントがそのリクエストを前提に開きます。「Issue のタイトルと作成者を取り出して Slack に投稿して」のように、必要なことを書き足して送信します。

アシスタントはリクエストを自分で読んでステップを提案し、適用するまで何も保存しません。

## ステップでリクエストを読む

リクエストごとに実行が 1 回始まり、実行履歴にはトリガーが **Webhook** と表示されます。ステップは、次の 2 つの環境変数からリクエストを読みます。

- `WEBHOOK_PAYLOAD`：送られてきた本文そのもの。
- `WEBHOOK_HEADERS`：ヘッダーの JSON。小文字の名前ごとに値のリストを持ちます（例：`{"x-github-event":["issues"]}`）。`Authorization` と Cookie は含まれません。

どちらも入力として宣言する必要はありません。JSON の本文から値を取り出すには、macOS と Windows で同じように動く `jq.filter` ステップを使います。

```yaml
steps:
  - id: issue
    action: jq.filter
    with:
      data: ${env.WEBHOOK_PAYLOAD}
      filter: .issue.title
    output:
      title: {from: stdout, decode: json}
```

後のステップは、タイトルを `${steps.issue.outputs.title}` として読めます。AI のステップには、本文全体をプロンプトの文章として渡せます。

本文は送り手が送ったものなので、信頼できない入力として扱ってください。コマンドでは、環境変数から読みます。macOS のシェルでは `"$WEBHOOK_PAYLOAD"`、Windows の PowerShell では `$env:WEBHOOK_PAYLOAD` です。`${env.WEBHOOK_PAYLOAD}` や、そこから取り出した値を、コマンドの文字列に直接書かないでください。引用符がコードとして解釈されてしまいます。[アシスタント](/ja/docs/ai/#the-assistant)はこれらの変数を知っているので、届くはずのリクエストを伝えてワークフローを作らせることもできます。

## 送り手を設定する

### GitHub

1. リポジトリまたは Organization の **Settings → Webhooks** を開き、**Add webhook** を選びます。
2. **Payload URL** に URL を貼り付けます。
3. **Content type** を `application/json` にします。GitHub の既定ではフォームデータ（`payload=…`）として送られ、JSON になりません。
4. **Which events would you like to trigger this webhook?** で **Let me select individual events** を選び、ワークフローに必要なイベントだけを選びます。GitHub が送るイベントごとに実行が始まります。

GitHub の **Recent Deliveries** タブでは、リクエストごとに Kitewell の応答を確認できます。リレーが受け付けたときは `202` です。

### そのほかのサービス

HTTP の `POST` を送れるサービスなら使えます。Stripe では、URL を指定してエンドポイントを追加し、イベントを選びます。Zapier や Make では、URL に POST する Webhook のアクションを追加します。フォームのサービスには、たいてい Webhook や「URL に通知」の設定があります。

## コンピューターがスリープ中やオフラインのとき

コンピューターに届くかどうかにかかわらず、リレーはすぐに送り手に応答します。リクエストはリレーで最大 7 日間待ち、Kitewell が再び接続すると古い順に実行されます。1 台のコンピューターに対して待てるのは 1,000 件までで、それを超えると送り手には後で再送するよう伝えます。

## 最近のリクエスト

Webhook の欄には、最新 20 件のリクエストが表示されます。届いた日時、送り手が付けたイベント名（GitHub の `issues · opened` や Stripe の `payment_intent.succeeded` など）、サイズ、結果です。開いている間、一覧は自動で更新されます。

**詳細** を選ぶと、リクエストの本文が読みやすく整えて表示され、ヘッダーとともにそれぞれ **コピー** できます。**このリクエストからステップを作る** と **実行を見る →** もここにあります。実行が始まらなかったリクエストは、本文が実行とともにしか保存されないため、代わりにその理由が表示されます。

| 結果 | 意味 |
| --- | --- |
| **実行を開始** | リクエストで実行が始まりました。リレーが同じリクエストを 2 回送っても、実行は 1 回です。 |
| **失敗** | 実行をキューに入れられませんでした（プロジェクトのエンジンが停止しているときなど）。エンジンが処理中や復旧中のときは、Kitewell が 10 分間再試行してから失敗とします。 |
| **無視** | Kitewell Pro が失効しています。 |

## URL を秘密にする

URL を知っている人は誰でもワークフローを開始できます。パスワードと同じように扱ってください。

- **新しい URL** を選ぶとすぐに置き換わり、古い URL は `404` を返します。古い URL を貼った場所すべてに、新しい URL を貼り直してください。
- **オフにする** も同じく URL を止めます。もう一度オンにすると、新しい URL になります。

Webhook の URL は 1 台のコンピューターのものです。同じワークフローの Webhook をチームメンバーのコンピューターでオンにすると、そのコンピューター用の URL になります。バックアップから復元すると、Webhook はオフの状態から始まります。

## 制限

| 制限 | 値 |
| --- | --- |
| リクエストの本文 | 512 KiB までのテキスト |
| URL ごとのリクエスト | 1 分あたり 60 件 |
| コンピューターを待つリクエスト | 1,000 件、最大 7 日間 |

リレーの応答：

| ステータス | 意味 |
| --- | --- |
| `202` | 受け付けました。本文は `{"id": "…"}` です。 |
| `404` | Webhook の URL ではないか、オフにされたか、置き換えられました。 |
| `413` | 本文が 512 KiB を超えています。 |
| `415` | 本文が UTF-8 のテキストではありません。 |
| `429` | この 1 分で 60 件を超えました。`Retry-After` の秒数の後に再送してください。 |
| `503` | このコンピューター宛てに 1,000 件がすでに待っています。 |

Windows では、本文が約 30,000 文字を超えると実行を開始できず、リクエストが **失敗** になることがあります。GitHub の push や pull request のイベントは、その大きさになることがあります。修正を予定しています。

Kitewell Pro が失効しても URL はリクエストを受け付けますが、何も開始せず **無視** と表示されます。再び登録しても、URL を作り直す必要はありません。

## リクエストの行き先

リクエストは、Cloudflare 上の Kitewell のリレー（hooks.kitewell.app）を通過します。リレーはコンピューターが受け取るまで、最大 7 日間だけリクエストを保持し、各 URL の秘密の部分はハッシュとしてのみ保存します。コンピューターでは、本文はほかの実行の入力と同じく実行とともに、設定した保持期間だけ残ります。[コンピューターの外に出るもの](/ja/docs/data-flow/)を参照してください。

## トラブルシューティング

- **「Kitewell のリレーから URL を取得しています…」が消えない。** Kitewell が Dagu Cloud にサインインしていて、コンピューターがオンラインか確認し、Webhook をオフにしてからオンにしてください。
- **新しい URL が `404` を返す。** Kitewell が新しい URL をリレーに伝えるまで、数秒待ってください。
- **GitHub からの本文をステップで解析できない。** GitHub の Webhook で **Content type** を `application/json` にしてください。
- **リクエストが失敗になる。** 行に理由が表示されます。プロジェクトが停止している場合は、メニューバーまたはトレイのメニューから開始し、リクエストをもう一度送ってください。
