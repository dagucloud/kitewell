---
title: チームでワークフローを共有
---

ワークフローを一度作成すれば、そのプロジェクトを別のデバイス、チームメイト、組織内の別のチームと共有できます。各デバイスは、自身の認証情報で独自のコピーを実行できます。チームメイトは、MCP や REST のクライアントから、共有する 1 台のホスト上のワークフローを操作することもできます。変更後もすべてのコピーを同じ状態に保つには、代わりに[プロジェクトを Dagu Cloud と同期](/ja/docs/cloud-sync/)してください。

## プロジェクトを別のデバイスに送る

1. プロジェクトセレクターを開き、**プロジェクトを管理** を選びます。
2. プロジェクトの横にある **エクスポート** を選びます。Kitewell が `.tgz` 形式のプロジェクトアーカイブをダウンロードします。
3. チームで決めた手段でファイルを共有します。
4. 受け取る側のデバイスで **プロジェクトを管理 → プロジェクトをインポート** を開き、アーカイブを選択します。同じ名前のプロジェクトがすでにある場合は、別の名前を選びます。
5. インポート後に表示される必要な準備を確認し、プロジェクトを開いて、そのデバイスの認証情報とツールを設定します。

インポートすると新しいプロジェクトが作成され、既存のプロジェクトは置き換えられません。インポートしたプロジェクトは、そのデバイスのプロジェクト数の上限に含まれます（無料プランでは 1 つ、Pro では最大 10 個）。プランの上限（無料プランでは 10 個、Pro では 200 個）を超えるワークフローを含むプロジェクトはインポートできません。

## プロジェクトに含まれるもの

アーカイブには、ワークフロー定義とスケジュール、名前付きのエージェントとモデル、インポートした OpenAPI 仕様と API 接続設定、サーバーのアドレスとグループ、キュー、イメージレジストリの定義、保存したバッチ入力セット、プロジェクトのワークフロー既定値が含まれます。API 接続はシークレットの参照を保持します。API アクションを実行する前に、インポートしたプロジェクトでそれらのシークレットを作成するか、そのプロジェクト内の別のシークレットを選んでください。

受け取る側のデバイスでは、次のものを独自に用意します。

- 管理されたシークレットの値とレジストリのパスワード。
- SSH 秘密鍵のパスと承認済みのホスト鍵。
- カスタムエージェントのコマンド、インストール済みのツール、エージェントのサインイン。
- 外部スクリプト、入力ファイル、Docker でマウントするデータ。

実行履歴、ログ、デバイス設定、Kitewell のクライアント API キーは、プロジェクトのエクスポートに含まれません。アーカイブは暗号化されていません。ワークフローのコマンド、OpenAPI 仕様、ソース URL、その他のプロジェクト設定に直接入力した認証情報は、自動的には削除されません。アーカイブを共有する前に、これらの項目を確認してください。

## スケジュールを実行する場所を選ぶ

インポートしたワークフローは一時停止の状態で届きます。手動で動作を確認してから、このデバイスで実行するワークフローについてのみ、保存済みのスケジュールを有効にしてください。

2 台のデバイスで同じスケジュールを有効にすると、それぞれが独立して実行します。一度だけ実行すべきチームの定型作業では、実行ホストを 1 台選び、ほかのコピーのスケジュールは一時停止のままにしてください。そのホストは、スケジュールされた時刻に起動していて利用可能である必要があります。詳しくは[スケジュールとバックグラウンド動作](/ja/docs/scheduling/)を参照してください。

## 共有する定義をバージョン管理する

プロジェクトの定義は、通常の JSON ファイルと YAML ファイルです。チームは自分たちの Git リポジトリで、これらをレビューし、バージョン管理できます。Kitewell がそのリポジトリへのプッシュ、プル、マージを代行することはありません。

macOS では、各プロジェクトの持ち運び可能なファイルは次の場所にあります。

```text
~/Library/Application Support/Kitewell/data/workspace/project-<id>/
  project.json
  workflows/
  batch-sets/
  agents/  apis/  queues/  registries/  server-groups/  servers/
```

`project.json` にはプロジェクト名、説明、ワークフロー既定値が、`workflows` にはワークフローファイルが、`batch-sets` には保存したバッチ入力が格納されます。その他の各フォルダーには、エージェント、API、キュー、レジストリ、サーバーグループ、サーバーごとに 1 つの JSON ファイルが格納されます。`project-<id>` フォルダー全体をバージョン管理してください。正しいディレクトリを特定するには、`project.json` 内のプロジェクト名を使います。そのプロジェクトに更新を適用するときは、既存のファイル構成とドキュメント ID を維持してください。

ファイルを置き換えたり、バージョン管理からの変更を適用したりする前に Kitewell を終了し、競合を解決してから Kitewell を再度開き、実行前にプロジェクトを確認してください。Kitewell のデータフォルダー全体ではなく、このプロジェクトの持ち運び可能なファイルを共有してください。デバイスの認証情報、シークレット、実行データは各ホストに属するものです。新たに受け取る人は、**プロジェクトをインポート** を使って、確認済みのエクスポートから始められます。

プロジェクトのエクスポートはスナップショットです。共有後に加えた変更は、ほかのデバイスに自動的には反映されません。新しいエクスポートを配布するか、チームの手順に沿ってバージョン管理しているファイルを更新するか、[プロジェクトを同期](/ja/docs/cloud-sync/)してください。

## 1 台のホストで共同作業する

チームの 1 台のマシンで実行するワークフローの場合は、**このデバイス → MCP** で、クライアントごとに個別の API キーを作成します。各クライアントのロールに応じて、**読み取り専用**、**ジョブの実行**、**編集と実行** のいずれかを選びます。チームメイトは、対応する MCP または REST クライアントを使って、そのホスト上のワークフローを確認、実行、編集します。

各キーは、そのクライアントが必要とするプロジェクトに限定してください。キーは、一覧に含まれないプロジェクトにはアクセスできません。ただし、どのワークフローもホストのユーザーとして実行されるため、プロジェクトの制限はオペレーティングシステムのサンドボックスではありません。ローカルのグラフィカルインターフェースと、任意で設定できるそのログインは、ホストのオーナーが管理します。これらの API キーで個別の GUI アカウントが作成されるわけではありません。

リモートのクライアントには、到達可能な HTTPS エンドポイントと、ご自身で用意する安全なネットワーク構成が必要です。Kitewell はホスト型の実行マシンを提供しません。接続と権限の詳細は [MCP と API アクセス](/ja/docs/mcp/)を参照してください。
